2. Pourquoi l'attracteur draw se forme

Réseau aléatoire → valeur ≈ 0 pour tout état
↓
MCTS guided par valeur ≈ 0 → exploration aléatoire → parties longues
↓
70 % des parties atteignent le plafond (300 coups) → outcome = DRAW = cible 0
↓
Buffer rempli de (état, cible=0) → réseau apprend "tout vaut 0"
↓
value_std → 0 → gradient de valeur → 0 → réseau figé sur "tout = draw"
↓ ↑ boucle fermée

La clé : les positions de Nine Men's Morris sont théoriquement nulles avec un jeu parfait (Gasser 1993). Le réseau a raison d'apprendre que "tout est draw" — le problème est que ce plateau est stable avant que le réseau n'ait appris à jouer. Il s'y installe avant d'avoir vu assez de parties décisives pour discriminer les positions.

Asymétrie fondamentale
Les draws fournissent un signal dense, stable et cohérent (cible = 0 toujours). Les wins/losses sont rares, bruités, et se contredisent souvent (position P jouée par A → +1, jouée par B → −1 selon qui gagne). Le réseau optimise naturellement en faveur du signal le plus stable = draws.

3. Pourquoi la categorical head n'a pas suffi

La categorical head (KataGo-style) aide à éviter un problème spécifique : le lazy-mean collapse où une value head MSE prédit 0 pour tout car c'est le minimum de E[(z)²] quand z ∈ {−1, 0, +1}. La categorical cross-entropy force le réseau à prédire une distribution, pas juste une moyenne.

Mais notre run montre que ça n'a pas suffi. Voici pourquoi :

ProblèmeCe que categorical head résoutCe qu'elle ne résout pas
Draw rate 73 % dans le buffer Peut correctement modéliser P(draw)=0.73 P(win)−P(loss) ≈ 0 quand P(draw) domine → même signal MCTS nul
value_std collapse Réduit le risque de tout prédire exactement 0 Si P(draw) ≈ 1 partout, scalar = P(win)−P(loss) ≈ 0 partout quand même
Distribution d'outcomes Meilleure calibration win/draw/loss Mais si le buffer ne contient que des draws, calibration = "tout vaut draw"
Insight clé
La categorical head résout un problème d'architecture (lazy-mean collapse). L'attracteur draw est un problème de distribution de données — le buffer contient 73 % de draws donc le réseau apprend correctement que "tout est draw". Aucun changement de loss function ne peut corriger une mauvaise distribution de données d'entraînement.

4. Solutions — du plus simple au plus complet

✓ Recommandé · Immédiat

A. Tiebreaker pièces/moulins à la limite de coups (ton idée)

Au lieu de déclarer DRAW quand la partie atteint 300 demi-coups, on déclare WINNER = le joueur avec le plus de pièces sur le plateau. En cas d'égalité stricte, on utilise le nombre de moulins comme second critère, et seulement sinon : DRAW.

Pourquoi c'est sound : dans Nine Men's Morris, les pièces sur le plateau sont l'objectif. Réduire l'adversaire à < 3 pièces = victoire. Avoir plus de pièces à la limite = position matériellement supérieure = on aurait probablement gagné avec plus de temps. C'est un proxy exact de la qualité de jeu.

✓ Avantages
  • Élimine ~60 % des draws synthétiques dans le buffer
  • Signal de valeur binaire clair sur des positions auparavant bruitées
  • Proxy réaliste : plus de pièces = réellement en train de gagner
  • 1 changement de code dans _assign_value_targets
  • Compatible avec tous les checkpoints existants
✗ Limites
  • Outcomes synthétiques ≠ vraies règles (mais OK pour l'entraînement)
  • Peut inciter à accumuler des pièces plutôt qu'à former des moulins tactiques
  • Agent entraîné joue différemment de la règle officielle en éval

Implémentation dans self_play.py

def _tiebreak_outcome(state: GameState) -> Outcome | None:
    """Déclare le winner par pièces à la limite de coups."""
    from morris_rl.env.rules import pieces_on_board
    p1 = pieces_on_board(state.board, 1) + state.pieces_in_hand[0]
    p2 = pieces_on_board(state.board, 2) + state.pieces_in_hand[1]
    if p1 > p2: return Outcome.PLAYER_1_WINS
    if p2 > p1: return Outcome.PLAYER_2_WINS
    # Égalité stricte : second critère = moulins
    mills1 = count_mills(state.board, 1)
    mills2 = count_mills(state.board, 2)
    if mills1 > mills2: return Outcome.PLAYER_1_WINS
    if mills2 > mills1: return Outcome.PLAYER_2_WINS
    return None  # vrai draw

✓ Recommandé · Complémentaire

B. Curriculum pieces_per_player=3 (au lieu de 4)

Avec 3 pièces par joueur (0 en main), le plateau est quasi-terminal. Une capture immédiate = fin de partie. Le signal de valeur est binaire et non-ambigu : "est-ce que je peux capturer maintenant ?"

Avec 4 pièces, il reste 3 captures avant la fin → les parties peuvent encore s'éterniser. Avec 3 pièces, la première capture termine tout → positions ultra-décisives même avec un réseau faible.

◎ Complémentaire · Moyen terme

C. Cible de valeur continue (pièce-diff normalisée)

Au lieu de cible ∈ {−1, 0, +1}, utiliser la différence de pièces normalisée à la fin de partie comme valeur cible. Cela transforme le problème de classification 3-classes en régression continue. 

# Dans _assign_value_targets, au lieu de v = ±1 ou 0 :
def _piece_diff_value(final_state, player) -> float:
    p_mine = pieces_on_board(final_state.board, player)
    p_opp  = pieces_on_board(final_state.board, opponent(player))
    # Normalisé dans [-1, 1]. +1 = 9 pièces d'avance (max théorique).
    return (p_mine - p_opp) / 9.0

# Pour les parties décisives, garder ±1 (c'est la vraie info)
# Pour halfmove_cap (was draw) → utiliser piece_diff_value
if outcome is None or outcome == Outcome.DRAW:
    if term_reason == "halfmove_cap":
        v = _piece_diff_value(final_state, player)  # signal continu
    else:
        v = 0.0  # vrai draw (threefold, etc.)

Compatibilité : fonctionne avec la categorical head (clamp la cible à {-1, 0, +1}) ou avec une value head scalaire MSE classique. Pour la categorical, il faudrait adapter le label mapping pour accepter des valeurs continues.

◎ Efficace · Contempt MCTS

D. MCTS Contempt — biaiser la recherche contre les draws

Inspiré de Stockfish et de travaux récents (Search-Contempt arXiv:2504.07757). Pendant le self-play, modifier le backup de valeur MCTS pour pénaliser les positions de draw : ajouter un petit biais vers les actions qui mènent à des positions décisives. 

# Dans _make_local_eval_fn (search.py), appliquer un contempt :
CONTEMPT = 0.10  # ajustable, 0.0 = désactivé

def evaluate(state) -> tuple:
    ...
    v = float(value[0].item())
    # Pousser légèrement les valeurs vers ±1, jamais vers 0
    # sign(v) * (|v| + CONTEMPT * (1 - |v|))
    import math
    sign = 1.0 if v >= 0 else -1.0
    v_contempt = sign * (abs(v) + CONTEMPT * (1.0 - abs(v)))
    return {a: float(probs[a]) for a in legal}, v_contempt

Effet : dans les positions symétriques (v≈0), MCTS explore plus agressivement les branches décisives plutôt que de tourner en rond. Ne change pas les valeurs d'entraînement, seulement la distribution des parties générées.

★ Stretch · Long terme

E. Positions curriculum asymétriques (déséquilibre matériel)

Au lieu de générer des positions symétriques (N vs N pièces), générer des positions déséquilibrées : 3 vs 5 pièces, 2 vs 4, etc. Dans ces positions, l'avantage matériel est flagrant et le signal de valeur est clair même avec un réseau faible. 

# Dans random_late_game_state (rules.py), ajouter un mode asymétrique :
def random_asymmetric_state(rng, min_pieces=2, max_pieces=5) -> GameState:
    p1_pieces = rng.integers(min_pieces, max_pieces + 1)
    p2_pieces = rng.integers(min_pieces, max_pieces + 1)
    # Garder une asymétrie minimale pour que la position soit décisive
    while abs(p1_pieces - p2_pieces) < 1:
        p2_pieces = rng.integers(min_pieces, max_pieces + 1)
    ...

Ces positions ont un "answer" clair : le joueur avec plus de pièces devrait gagner. Le réseau peut apprendre ce signal directement, sans dépendre d'une résolution de longue partie.
